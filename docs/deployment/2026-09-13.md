## Cache migration caveat

An existing browser session continued to load the old `index-DeJNM5kz.js` bundle
and two manifest links after ordinary reloads, while direct HTTP requests already
returned the new deployment. A second tab sharing that browser context also saw
the old version. To isolate server readiness, the smoke above temporarily bypassed
the Service Worker and browser cache in the test tab. Both overrides were restored
afterward.

This proves the new server deployment and its processing flow; it does **not**
prove automatic adoption by every existing cached client. The exact source of
the old-cache retention was not isolated. No destructive cache clear or forced
activation was used. A real old-client-to-new-client update with in-memory work
remains an explicit follow-up, including waiting-worker detection, deferred update,
and safe activation after queue/results are cleared. Do not instruct users to
reload while they still need in-memory files or outputs.
